# Digital FTE Constitution

**Version**: 3.0.0 | **Ratified**: 2026-02-11 | **Last Amended**: 2026-04-14

> This constitution is the supreme governance document for the Digital FTE
> project. It is established once and amended only through the versioned
> amendment procedure defined in the Governance section. It MUST NOT be
> recreated, replaced, or re-initialized at any point in the project lifecycle.

---

## Core Principles

### I. Local-First Autonomous Operations

This project MUST build a local-first autonomous AI employee for business
operations. All processing, file management, and task execution MUST occur on
the local machine without requiring cloud services for core functionality.
External APIs MAY be used for AI inference and authorized external actions but
MUST NOT be required for file operations, scheduling, or task orchestration.

Local-first applies at every tier. No tier upgrade permits replacing local
storage, local orchestration, or local audit logs with cloud-only equivalents.

### II. Canonical Folder Structure

All managed workspaces MUST use the following directory convention. Directories
are grouped by function. No feature or automation MAY create, rename, or bypass
canonical directories. New subdirectories within them are permitted when
justified by a spec.

**Core triage directories:**

- `/Inbox` — Incoming items awaiting triage
- `/Needs_Action` — Items requiring human or AI decision
- `/Needs_Action/plans` — Runtime triage plan files generated by the orchestrator
- `/Plans` — Persistent, named plans authored or approved for long-term reference
- `/Pending_Approval` — Proposed external actions awaiting human sign-off
- `/Approved` — Execution plans and scripts cleared to run; approved external actions
- `/Rejected` — Actions reviewed and explicitly rejected by the human operator
- `/Done` — Completed artifacts and archived results

**Operations directories:**

- `/Logs` — Execution logs, audit trails, and error records (append-only)
- `/In_Progress` — Active tasks and work-in-progress items

**Intelligence and reporting directories:**

- `/Briefings` — Generated summaries, CEO briefings, and weekly audit reports
- `/Updates` — Status updates and changelogs produced by the system
- `/Signals` — Detected patterns, anomalies, and proactive suggestions

**Business directories:**

- `/Accounting` — Draft invoices, payment records, and accounting event logs

### III. Tiered Scope

Feature implementation is governed by ratified tiers. Higher tiers subsume
lower-tier capabilities. Work outside the highest ratified tier MUST NOT begin
without constitution amendment.

**Bronze Tier** (ratified 2026-02-11):

1. **Obsidian vault management** — reading, organizing, tagging, and
   summarizing notes within an Obsidian-compatible vault.
2. **Local file monitoring** — watching designated directories for new or
   changed files and routing them through the canonical folder structure.

**Silver Tier** (ratified 2026-02-12, completed 2026-04-14):

3. **Gmail monitoring** — Gmail API with OAuth; unread emails converted to
   Markdown and routed to `/Inbox/email/` or `/Needs_Action/email/`.
4. **WhatsApp monitoring** — Playwright browser automation; unread threads
   converted to Markdown and routed to `/Inbox/whatsapp/` or
   `/Needs_Action/whatsapp/`.
5. **Reasoning loop with HITL** — orchestrator classifies emails, generates
   draft replies, and writes runtime plan files to `/Needs_Action/plans/`
   before any action is taken.
6. **MCP server** — vault MCP server exposing `list_files`, `read_file`,
   and `write_file` tools for Claude Code integration.

**Gold Tier** (ratified 2026-04-14):

7. **Cross-domain integration** — unified routing across personal and business
   workflows with stable vault state boundaries.
8. **Odoo accounting integration** — draft-only accounting actions with
   approval-gated invoice and payment workflows.
9. **Social media publishing** — Facebook, Instagram, and X integration with
   approval-safe posting and summary generation.
10. **Weekly CEO briefing** — automated audit flow, bottleneck detection, and
    Monday Morning CEO Briefing generation.
11. **Reliability and autonomous completion** — error recovery, graceful
    degradation, and Ralph Wiggum loop integration for multi-step flows.

### IV. Safety-First Execution

The system MUST NOT execute any system-modifying action — file moves,
deletions, renames, shell commands, API calls with side effects, external
messages, or financial operations — without first writing a human-readable
execution plan. The plan MUST include:

- Action description and all affected paths or external targets
- Rollback strategy
- Expected outcome

For **local actions**: the plan MUST be written to `/Approved` before execution.

For **external actions** (anything visible outside the local machine): the plan
MUST be written to `/Pending_Approval` first. The human operator MUST move it
to `/Approved` to authorize execution. The system MUST NOT self-approve.

Emergency overrides are not permitted at any tier.

### V. Persistent Retry Logic (Ralph Wiggum Loop)

When a task fails, the system MUST retry up to **3 times**:

1. **Attempt 1**: Execute as planned.
2. **Attempt 2**: Re-read context, adjust parameters, retry.
3. **Attempt 3**: Simplify to minimal viable action, retry.
4. **After 3 failures**: Log the failure to `/Logs` with full context and
   move the task to `/Needs_Action` for human review.

The system MUST NOT silently drop failed tasks or retry indefinitely. This
loop MUST be applied to all multi-step autonomous flows in Gold Tier.

### VI. Human-in-the-Loop and Approval Gates

Any operation that sends data to, modifies state in, or is visible to parties
outside the local machine is an **external action** and requires explicit human
approval before execution.

**Approval-gated actions** — the system MUST write a proposal to
`/Pending_Approval` and wait for human promotion to `/Approved` before
proceeding with any of the following:

- Sending, replying to, or forwarding emails or messages
- Publishing posts to any social media platform (Facebook, Instagram, X)
- Creating, submitting, or paying invoices or any financial transaction
- Any Odoo write operation (invoices, payments, journal entries)
- Any external API call that modifies remote state

**HITL workflow:**

1. System writes proposed action to `/Pending_Approval/<domain>/<slug>.md`
   with: action description, target, payload, expected outcome, rollback.
2. Human reviews and moves to `/Approved/<domain>/` to authorize.
3. System executes and logs result to `/Logs` with full context.
4. Rejected proposals are moved to `/Rejected` with a human-written reason.

**No self-approval**: The system MUST NOT move items from `/Pending_Approval`
to `/Approved` autonomously. That transition is a human-only action.

### VII. Credential and Secrets Isolation

No secrets, API keys, OAuth tokens, passwords, or credentials of any kind MAY
appear in vault content, committed source files, or generated Markdown files.

**Rules:**

- All credentials MUST be stored in `.env` files excluded from version control.
- OAuth tokens MUST be stored in `.watcher-state/` or `.secrets/`, both of
  which MUST be listed in `.gitignore`.
- Playwright session cookies MUST be stored in `.watcher-state/` and excluded
  from version control.
- Vault files (in `/Inbox`, `/Needs_Action`, `/Plans`, `/Approved`, `/Done`,
  `/Briefings`, `/Accounting`, `/Logs`, etc.) MUST contain zero credentials.
  If a captured item contains a credential, it MUST be redacted before writing.
- Odoo connection credentials MUST be stored in `.env` only. They MUST NOT
  appear in any spec, plan, task, log, or briefing file.

### VIII. Agent Skills and MCP Orchestration

All repeatable AI capabilities MUST be implemented as agent skills where
applicable. External system integrations MUST use MCP tools rather than
ad-hoc direct API calls within orchestrator code.

**Agent skills:**

- Repeatable, parameterized AI tasks (classify email, generate briefing,
  detect anomaly, draft reply) MUST be implemented as named, documented
  skills callable from the orchestrator.
- Skills MUST be independently testable without requiring the full
  orchestrator to be running.

**MCP orchestration:**

- External actions (vault read/write from Claude Code, Odoo operations,
  social media posting) MUST be exposed as MCP tools.
- The MCP server MUST enforce path safety, authentication, and rate limits
  at the tool boundary.
- New Gold-tier external integrations MUST define their MCP tool contract
  in a `contracts/` directory within the feature spec before implementation.

### IX. Audit Logging

Every meaningful automated action MUST produce a log entry in `/Logs`.

**Log entry requirements** (all fields mandatory):

- `timestamp` — ISO 8601 datetime
- `action_type` — identifier for the action class
- `source_path` — origin file or resource
- `dest_path` — destination file or resource (if applicable)
- `outcome` — `success` | `failure` | `partial`
- `details` — human-readable description including reason and any plan path

**Scope:** Logging is required for all triage decisions, file moves, draft
creations, plan writes, external action executions, approval state transitions,
briefing generations, accounting events, and retry loop outcomes.

Logs MUST be append-only. The system MUST NOT delete or modify existing log
entries. Log rotation is permitted but MUST preserve all entries in archive.

### X. Graceful Degradation

The system MUST continue operating at reduced capability when individual
components fail. No single-component failure MAY halt the entire system.

**Rules:**

- A failure to write a runtime plan MUST NOT halt triage of the email.
- A failure to reach an external API MUST trigger the Ralph Wiggum Loop
  (Principle V) and route to `/Needs_Action` after exhaustion — it MUST NOT
  crash the watcher or orchestrator process.
- A missing `/Approved` action MUST result in the item being held in
  `/Pending_Approval`, not discarded.
- Each watcher and orchestrator component MUST handle its own exceptions,
  log them, and remain running for the next cycle.
- Gold Tier automation MUST remain partially operational if Odoo, Gmail,
  WhatsApp, or social media integrations are individually unavailable.

### XI. Gold-Tier Phased Development

Gold Tier is structured into five sequential phases. Each phase MUST be
completed and explicitly confirmed before the next phase begins. Phases MUST
NOT be skipped, reordered, or combined. Each phase is scoped exclusively to
its own spec folder.

**Phase 1 — Cross-Domain Integration Foundation**
Scope: `specs/gold/phase-1/`

- Unify personal and business vault routing under a single orchestrator
- Stabilize vault state boundaries and shared directory contracts
- Confirm MCP orchestration boundaries for all Gold-tier integrations
- Verify all Silver-tier functionality remains intact under Gold-tier routing

**Phase 2 — Odoo Accounting Integration**
Scope: `specs/gold/phase-2/`

- Integrate with Odoo Community for accounting event capture
- Implement draft-only accounting actions (no write without approval)
- Approval-gated invoice and payment workflows via `/Pending_Approval/`
- Accounting event logging to `/Accounting/` and `/Logs/`

**Phase 3 — Social Media Expansion**
Scope: `specs/gold/phase-3/`

- Facebook and Instagram integration (posting + summary generation)
- X (Twitter) integration (posting + summary generation)
- All posts approval-gated via `/Pending_Approval/social/`
- Approval-safe publishing flow with rollback capability

**Phase 4 — Weekly Audit and CEO Briefing**
Scope: `specs/gold/phase-4/`

- Automated business and accounting audit flow
- Monday Morning CEO Briefing generation to `/Briefings/`
- Bottleneck detection and proactive suggestion writing to `/Signals/`
- Weekly summary generation from vault activity

**Phase 5 — Reliability and Autonomous Completion**
Scope: `specs/gold/phase-5/`

- Error recovery and fault-tolerant multi-step completion
- Graceful degradation implementation across all integrations
- Watchdog and process resilience (auto-restart, backoff)
- Ralph Wiggum Loop integration for all Gold-tier multi-step flows

**Phase Execution Rules:**

For each phase, execute in this exact order using SpecifyPlus commands:

1. `/sp.specify` — Create spec scoped to the phase folder only
2. `/sp.plan` — Generate plan based strictly on the approved spec
3. `/sp.tasks` — Create small, verifiable, non-expanding tasks
4. `/sp.implement` — Execute only tasks from the approved spec

A phase is closed only after **explicit user confirmation**. The system MUST
NOT auto-start the next phase or conflate work between phases.

### XII. Gold Scope Boundary Enforcement

No implementation work MAY begin outside an approved, phase-scoped spec.

**Prohibitions:**

- MUST NOT implement features belonging to a future phase while a current
  phase is open.
- MUST NOT expand a phase spec during implementation — scope changes require
  a new `/sp.specify` amendment, not inline additions to tasks.
- MUST NOT modify `.specify/` internal folders, `.claude/` command
  definitions, or SpecifyPlus scripts under any circumstance.
- MUST NOT recreate or replace this constitution. Amendments MUST use the
  versioned amendment procedure in the Governance section.
- MUST NOT combine or skip `/sp.specify` → `/sp.plan` → `/sp.tasks` →
  `/sp.implement` steps. Each step is a prerequisite for the next.
- MUST NOT begin Phase N+1 without explicit user confirmation that Phase N
  is closed.

**Specs are contracts**: Once a spec is approved and implementation has begun,
its requirements are binding. Deviations require a formal amendment, not a
silent change.

## Operational Constraints

- **No secrets in vault or code**: All API keys, tokens, and credentials
  MUST be stored in `.env` files excluded from version control.
- **Smallest viable diff**: Changes MUST be minimal and focused.
  Do not refactor unrelated code alongside feature work.
- **Audit trail**: Every automated action MUST produce a log entry in
  `/Logs` with timestamp, action type, and outcome (Principle IX).
- **Obsidian compatibility**: Files written to the vault MUST be valid
  Markdown compatible with Obsidian (YAML frontmatter, `[[wikilinks]]`,
  standard Markdown syntax).
- **Approval before action**: External actions MUST follow the HITL
  workflow (Principle VI). No external action without `/Pending_Approval`
  → human promotion → `/Approved` sequence.
- **One phase at a time**: Gold Tier phases are sequential and gated by
  explicit user confirmation (Principle XI, XII).

## Development Workflow

1. **Specify**: Define the feature via `/sp.specify`. Scope MUST be
   limited to the current phase folder.
2. **Clarify**: Resolve ambiguities via `/sp.clarify` before planning.
3. **Plan**: Architect the solution via `/sp.plan`. Plans MUST include
   a Constitution Check validating all twelve principles.
4. **Tasks**: Break the plan into ordered tasks via `/sp.tasks`.
5. **Implement**: Execute tasks via `/sp.implement`. Commit after each
   logical unit of work.
6. **Review**: All work MUST verify compliance with this constitution
   before the phase is confirmed closed.

## Governance

- This constitution is the supreme governance document for the Digital FTE
  project. It supersedes all other practices and conventions when conflicts
  arise. It is established once and MUST NOT be recreated.
- **Amendments** require: (1) a written proposal, (2) rationale documenting
  why the change is needed, (3) a migration plan for affected artifacts, and
  (4) a version increment per SemVer via `/sp.constitution`.
- **Versioning policy**:
  - MAJOR: Principle removals, redefinitions, or tier-level structural changes.
  - MINOR: New principles or material expansions to existing principles.
  - PATCH: Clarifications, wording corrections, typo fixes.
- **Compliance review**: Every `/sp.plan` output MUST include a Constitution
  Check section validating adherence to all twelve principles. Violations MUST
  be justified in a Complexity Tracking table or the plan is rejected.
- **Phase gating**: No Gold Tier phase may begin without explicit user
  confirmation per Principle XII. This confirmation MUST be recorded in the
  phase spec's history record.
